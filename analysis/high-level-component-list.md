# Intro

This document contains the High-level component list + responsibilities to facilitate dialog to align on final spec and implementation details for SPAS framework.

## Components

This section contains details about each SPAS component, one per H3 header.

### Sidecar/Mesh

Platform-injected proxy handling networking,  security, request/event I/O (transformations) and service invocation.

- Use DAPR in PoC
- DAPR manages all aspects related to sidecars, security, etc. In PoC we settle with defaults unless simpler with some non-default settings.
- gRPC: If we can save time in POC, we should allown communication between DAPR sidecar and SPAS service using HTTP protocol.
- No mTLS to begin with, but could be enabled later.
- Use DAPR Subscription component with routes for routing (see <https://docs.dapr.io/developing-applications/building-blocks/pubsub/howto-route-messages/>)
- Create DAPR Custom HTTP Middleware to execute inbound and outbound transformations as defined by choreography. This should ideally always run after the Subscription component logic if possible (need to check DAPR docs on this)
- Use DAPR standard observability features with Zipkin for distributed tracing in POC.
- DAPR sidecar invokes SPAS Service endpoints, either from the DAPR Subscription component (according to its routing configuration), or when called by the API gateway (note we have to decide if API gateway should be allowed to call SPAS Service directly or only via DAPR sidecar and according to DAPR sidecar contract).
- Identity propagation
  - For north-south communication DAPR sidecar propagates the identity to a SPAS Service according to standard agreed auth protocol which SPAS service must support (e.g. as in .Net Program.cs `services.AddAuthentication().AddMicrosoftIdentityWebApi(...)` and `app.UseAuthentication().UseAuthorization();` etc.).
  - For east-west communication in PoC, identity information flows as part of the event payload (CloudEvents extension or body property). The SDK provides utilities to extract this.
    - Middleware injection of identity headers is deferred to Production to simplify the PoC.

### SPAS Service

Packaged bounded contexts exposing APIs and producing various outbound events. May have external dependencies which must be explicitly allowed and configured.

- This is the service built by developers according to service-specification/03-service-model.md etc.
- In POC the example services would use SPAS SDK
- At Design-time SPAS service project has following folder structure (additional folders may be added but are not governed by SPAS spec)

    ```text
    ./
        /metadata (contains all metadata files as generated by SPAS service or manually authored by developers at design-time, see SPAS SDK/Design-time metadata endpoints)
            inbound.endpoints.json (A json describing the SPAS service inbound endpoints, with references to appropriate message schema files)
            outbound.events.json (A json describing the outbound event schemas with reference to appropriate message schema files)
            outbound.endpoints.json (A json describing the requirements for external outbound traffic, i.e. need to communicate with external services)
            runtime.json (A json describing the runtime section of metadata, i.e. the docker repository and image)
            security.data.json (A json describing the data security section of metadata, i.e. the data classification)
            {messageX}.json (A json schema for message X)
            {messageY}.json (A json schema for message Y)
            license.txt (i.e. a free text describing license)
    /config
        May contain service configuration files depending on what we decide during the implementation of SPAS SDK (see SPAS SDK/Configuration classes)
    /src (contains the SPAS service code)
        internals of this folder are left to developers choice and may include Dockerfile too.
    ```

  - Note how SPAS Service metadata is decomposed at design-time, which means that during publishing it will be composed into a single spas metadata json variant with accompanied message schemas, all to be stored in SPAS Repository backing store of our choice.
  - If wished, SPAS service can expose Design-time metadata endpoints, which can be used to get generated metadata instead of manually authoring it (see SPAS SDK/Design-time metadata endpoints).

- At Run-time
  - SPAS service is packaged as Docker container image as chosen by developers and with no particular requirements imposed by SPAS spec.
  - SPAS Service configuration depending on the design of SPAS SDK/Configuration classes component.
  - SPAS Service metadata IS NOT used at Run-time, but will be used during the Domain Choreography/Composition (see Domain Composition section)

### SPAS SDK

A Language/framework development kit to build SPAS compliant services.

- One per each chosen language/framework (in PoC we start with .Net/C#).
- SDK should contain abstract base classes, interfaces and common utilities, which makes bulding SPAS Service simpler. This includes:
  - Base classes to derive SPAS Service inbound endpoints from (i.e. in .Net the controller classes etc.)
    - If SPAS Service stores data classified as PII, than Service must also expose an endpoint to manage this data (get, delete, etc.) SDK could provide this as well, although only nice to have in POC (e.g. in .Net `app.UseSPASPiiEndpoints();` or similar).
  - If we plan to enforce gRPC in POC from the beginning (see gRPC under Sidecar/mesh), include methods/components to ensure SPAS Service supports gRPC protocol (e.g. in .Net `builder.Services.AddGrpc(); app.MapGrpcService<MySPASService>();` etc. see <https://learn.microsoft.com/en-us/aspnet/core/grpc/aspnetcore?view=aspnetcore-10.0&tabs=visual-studio>).
  - Metadata attributes and classes, which may depend on the implementation of Endpoints to retrieve SPAS Service metadata described under SPAS SDK/Design-time metadata endpoints
    - Attributes to decorate SPAS Service inbound endpoints with (i.e. in .Net the controller class and methods)
    - Attributes to decorate SPAS Service outbound event payload contracts with (i.e. the classes defining the payload contract for the events produced by the SPAS Service under the consideration)
  - Configuration classes, used to unify the way SPAS Services are configured (e.g. various settings specific to SPAS Service, such as connection strings and similar) hence ensuring configuration consistency and simpler management at runtime. As minimum SDK could provide:
    - Extensible configuration model unless we can reuse models from the framework under the consideration (i.e. .Net, Java etc.)
    - Appropriate abstractions for specific configuration storages (i.e. env variables, simple files, kubernetes config map, etc.)
    - Fetching secrets from vaults, such as Azure KeyVault, Hashicorp etc.
    - Note here to see if we can utilise DAPR to provide some implementation during POC
  - Utils/Services that
    - Allow SPAS Service to retrieve identity information (in PoC claims and id). Ideally method handles both noth-south and east-west communication. For East-West PoC, it extracts identity from the event payload.
    - Allow SPAS Service to publish events while ensuring at-least-once delivery guaranty by abstracting an outbox pattern implementation from the SPAS Service, thus further simplifying the work of SPAS service developer. In POC for .NET SDK we can utilise <https://github.com/dotnetcore/CAP>.
  - Base classes for Event schema (in PoC we start with DAPR and CloudEvent schema, which already includes tracing information, so we have to see how much implementation this requires beoynd the blow described payload)
    - Base class for Payload which contains standard element for Identity information.
    - Identity information could be JWT token containing all details including claims, etc.
    - In POC I don't see a need for base classes for contracts when implementing north-south communication since we plan on using DAPR which already provides contracts for both, distributed tracing and Identity handling. Do you agree?
  - Design-time metadata endpoints: are endpoints which can be used to retrieve SPAS Service metadata and SPAS Service contract schemas to be stored in SPAS repository at design-time. These endpoints should be exposed only in development/local environment at some standard route (e.g. depending on framework, developer can add this to its SPAS service, such as in .Net `ìf (app.Environment.IsDevelopment()){app.UseSPASDesignEndpoints();}` or similar). Note later how this endpoint can be used by SPAS CLI to generate spas.json when authoring SPAS Service to be published to SPAS repository.

### SPAS Repository

A service serving as a central repository to store published SPAS service metadata alongside their links to container images as well as service event/message schemas.

- SPAS repository is plain webapi with NoSQL document store to persist SPAS Service Metadata
  - Event/Message physical schemas are referenced using relative path
  - Event/Message physical schemas are also persisted inside SPAS Repository, either in NoSQL database or as files (to be decided)
- SPAS repository exposes HTTP endpoints with following operations
  - Create: add new SPAS Service.
    - Verb: POST
    - Arguments:
      - Name: Unique name of the service
      - Version: Semantic version of service
    - Payload:
      - Ideally a packaged SPAS Service metadata (presumably archive file) with metadata json (a single json file merged out of decomposed metadata + all relevant message schemas from SPAS Service design-time files located in /metadata folder).
    - Response: 201 + Unique SPAS Service Id (UUID and Version)
  - Update: Update existing SPAS Service
    - Verb: PUT
    - Arguments:
      - Name: Unique name of the service
      - Version: Semantic version of service (must be unique for the SPAS service with given Id)
      - Payload: Same as POST.
    - Response: 204 + unique SPAS Service Id and Version
  - List: List latest version of all SPAS Services available in repository matching given filter
    - Arguments (all optional): Name, BoundedContext name
    - Response: Json array with SPAS Services matching the criteria with following attributes:
      - Id
      - Name
      - Latest Version
      - Bounded Context
      - Date Created
  - Details: Get details of a single SPAS Service
    - Verb: GET
    - Arguments: Id
    - Response: A json object containing following attributes
      - Id
      - Name
      - Bounded Context
      - Array of versions
  - Pull: Download metadata for given SPAS Service version
    - Verb: GET
    - Arguments: Id, Version
    - Response: Same as POST payload (i.e. archive containing full service metadata including all referenced message schema files).
  - Remove: Delete specific version of SPAS service
    - Verb: DELETE
    - Arguments: Id, Version
    - Response: 204

### SPAS CLI

Allows developers to perform various tasks, such as:

- Support execution of all SPAS Repository operations
- Support work during Domain composition/choreography creation (e.g. order flow)
- Support configuring SPAS service adaptation rules (Event routing/DAPR subscription, Transformation rules etc.) for given Domain composition/choreography

There are envisioned two cli tools (spas-service and spas-choreography) each designed to support specific functionality as described below, which should reduce development complexity as well as it should simplify usability. This is however open for debate, i.e. single CLI tool cloud be acceptable with strong arguments.

#### spas-service

Designed to support developers developing SPAS Services with following commands which execute corresponding SPAS Repository methods.

- spas-service create (creates SPAS archive and sends it to SPAS Repository Create endpoint)
- spas-service list (see SPAS Repository List operation)
- spas-service details (see SPAS Repository Details operation)
- spas-service update (see SPAS Repository Update operation)
- spas-service remove (see SPAS Repository Remove operation)

Not needed for POC but if simple, we can extend above commands with validate or/and test operations, which may execute some of the operations normally used during Domain composition. E.g.

- spas-service validate (should presumably only run locally and validate all metadata files and their references, etc. by first downloading metadata by executing SPAS Repository Download operation.)

#### spas-compose

Designed to support developers developing Domain Compositions with following commands.

- spas-compose services list (see SPAS Repository List operation)
- spas-compose services details (see SPAS Repository Details operation)
- spas-compose context init (creates a folder/workspace for new Domain Context where all choreographies related to it will be worked on. This command would also create an empty docker-compose.yaml file to be used for local runtime)
- spas-compose services pull (Pulls all metadata for given SPAS service and unpacks its content to a given Domain Context folder/workspace. This uses SPAS Repository Pull operation first)
- spas-compose choreography init (creates new choreography.json file inside the folder for selected Domain Context, where choreographies can be configured)
- spas-compose choreography generate (reads corresponding `choreography.yaml` and creates all needed DAPR components including the transformation configuration files used by our custom DAPR HTTP Middleware. This operation should also update docker-compose.yaml which can be found inside Domain)

Not needed for POC but if simple, we can extend above commands with validate or/and test operations, which may execute some of the operations normally used during Domain composition. E.g.

- spas-service validate (should presumably only run locally and validate all metadata files and their references on already pulled SPAS Service metadata, etc.)

>Note: either `spas-compose choreography generate` or `spas-compose services pull` should update the `docker-compose.yaml` file, which is created by running `spas-compose context init`. This is to be decided.

### Domain Composition

Although Domain Composition is not an integral part of SPAS Framework, it is worth describing in this section how SPAS Services and SPAS CLI can be used to compose a fully functional application targeting specific Domain Context, while using one or more Domain choreographies.

When composing domain developer executes following actions in given order

- Create Git repo
- Create a new Domain Context inside the repo (e.g. my-e-commerce-admin for selling products over internet).
- Pull all required SPAS Services from SPAS Repository (e.g. my-products, my-orders, my-shipping and my-payments).
- Initiate choreography inside the created domain folder
- Configure choreography and glue it all together
- Run the application (in POC only locally using Docker compose unless there are simpler options)

Below is a example with folder structure inside such Git repo (.git and other standard files are omitted for brevity)

```text
./
    /services
        /my-products
            /metadata
                spas.json
            /schemas
                /inbound
                    update-stock.json
                /outbound
                    stock-updated.json
        /my-orders
            ...
        /my-stock
            ... 
        /my-shipping
            ...
        /my-payments
            ...
        /my-notifications
            ...            
    /domains
        /my-e-commerce-admin
            /schemas
                ProductCreated.json
                ProductRemoved.json
                StockUpdated.json
            /choreographies
                product-add.yaml (containing choreography configuration when products are created)
                product-remove.yaml (containing choreography configuration when products are removed)
                order-cancellation.yaml (containing choreography configuration when admin cancels a order)
            /.dapr
                /components
                    my-stock.subscription.yaml (contains DAPR subscription configuration for my-stock service subscribing to ProductCreated and ProductRemoved events)
                /transformations (contains transformations grouped per SPAS Service folder)
                  /my-stock (config files for transforming my-stock service inbound and outbound messages)
                    ProductCreated.yaml (transformation of event defined by domains/my-e-commerce-admin/schemas/ProductCreated.json schema to a message defined by services/my-products/schemas/inbound/update-stock.json, i.e. used to execute corresponding my-stock inbound endpoint.)
                    ProductRemoved.yaml (same as ProductCreated.yaml)
                    StockUpdated.yaml (transformation of outbound StockUpdated event payload defined by services/my-products/schemas/outbound/stock-updated.json schema to a Domain event defined by domains/my-e-commerce-admin/schemas/StockUpdated.json schema)
                  /my-products
                    ...
            docker-compose.yaml (standard docker-compose.yaml file containing all downloaded services, including their sidecars as well as with .dapr/transformations/{service} and .dapr/components folders loaded as volumes to be accessed by DAPR as well as DAPR HTTP Middleware when loading transformation configurations.)
        /my-e-commerce-public
            Contains same folder structure as /my-e-commerce-admin but for different choreographies with tailored workflows for public users, which purchase products...  
```
