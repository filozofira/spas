# Feature Specification: SPAS Sidecar Component

**Feature Branch**: `007-spas-sidecar`  
**Created**: 2025-12-14  
**Status**: Draft  
**Input**: User description: "Create SPAS Sidecar component according to principles and specifications - implements traffic interception, protocol translation, service invocation, transformation execution, and observability for autonomous service choreography"

## Context

The SPAS Sidecar is the core runtime component that mediates all service communication in a SPAS domain. A working prototype exists at `prototypes/spas-sidecar-prototype/` demonstrating the pattern. This feature productionizes the sidecar as a deployable component that:

1. Pairs with each service instance to handle all ingress/egress traffic
2. Executes JSONata transformations between domain and internal message formats
3. Publishes and subscribes to message broker topics (Redis in PoC)
4. Invokes service HTTP endpoints for command/query and event consumption patterns
5. Propagates W3C Trace Context through CloudEvents for distributed tracing
6. Loads configuration from files generated by `spas-compose choreography deploy`

The sidecar ensures **no direct service-to-service communication** - all traffic flows through sidecars, enabling transformation, observability, and policy enforcement at every boundary.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Configuration Loading (Priority: P1)

As a developer using spas-compose, I want the sidecar to load configuration from mounted JSON files so that choreography definitions drive sidecar behavior.

**Why this priority**: Configuration is the foundation - all other operations (publishing, subscription, commands) depend on loaded configuration to know topics, endpoints, and transformations.

**Independent Test**: Mount `config.json` file with inbound/outbound entries; verify sidecar loads and validates configuration on startup.

**Acceptance Scenarios**:

1. **Given** valid `config.json` with inbound and outbound entries, **When** sidecar starts, **Then** configuration is loaded and validated successfully
2. **Given** invalid configuration (missing required fields), **When** sidecar starts, **Then** startup fails with clear error messages listing validation issues
3. **Given** legacy configuration format (subscriptions/publications), **When** sidecar starts, **Then** auto-migrates to new format with warning logged

---

### User Story 2 - Event Publishing (Priority: P1)

As a service developer, I want my service to publish events through the sidecar so that events are transformed, wrapped in CloudEvents format, and delivered to the message broker with trace context preserved.

**Why this priority**: Publishing is the fundamental outbound operation. Without it, services cannot participate in choreography.

**Prerequisite**: US1 (Configuration Loading) - requires `outbound` configuration.

**Independent Test**: Service POSTs to sidecar `POST /publish` endpoint with payload and required headers (`x-event-type`, `x-service-name`, `x-correlation-id`); verify sidecar resolves topic from routing config and message appears in Redis stream with CloudEvents wrapper and correct trace context.

**Acceptance Scenarios**:

1. **Given** a service with sidecar configured with outbound routing `com.example.order.created` → `orders-requested`, **When** service POSTs to `/publish` with JSON payload, `x-event-type: com.example.order.created`, and `traceparent` header, **Then** sidecar resolves topic from routing config and publishes CloudEvents-wrapped message to Redis stream `orders-requested` with trace context preserved
2. **Given** a service with outbound transformation configured, **When** service publishes event, **Then** sidecar applies JSONata transformation before publishing
3. **Given** a service publishes without `traceparent` header, **When** sidecar receives request, **Then** sidecar generates new W3C trace context and includes in CloudEvents envelope

---

### User Story 3 - Event Subscription & Service Invocation (Priority: P1)

As a service developer, I want the sidecar to consume events from subscribed topics and invoke my service's HTTP endpoint so that my service receives transformed events with trace context propagated.

**Why this priority**: Subscription completes the event-driven loop. Combined with publishing, enables full choreography participation.

**Prerequisite**: US1 (Configuration Loading) - requires `inbound` configuration with `kind: event`.

**Independent Test**: Publish event to Redis stream; verify sidecar consumes, transforms, and invokes configured service endpoint with CloudEvents payload and trace headers.

**Acceptance Scenarios**:

1. **Given** sidecar configured with inbound event subscription to `orders-requested` with `invokeEndpoint: /incoming`, **When** CloudEvents message appears in stream, **Then** sidecar invokes service at `POST /incoming` with transformed payload and `traceparent` header
2. **Given** inbound transformation is configured, **When** sidecar consumes event, **Then** JSONata transformation is applied before invoking service
3. **Given** event contains `traceparent` in CloudEvents envelope, **When** sidecar invokes service, **Then** same trace context is propagated in HTTP headers

---

### User Story 4 - Command Invocation (Priority: P1)

As a client or orchestrator, I want to invoke service commands through the sidecar so that request-response patterns work with transformation and tracing.

**Why this priority**: Commands enable synchronous request-response patterns essential for queries and immediate actions.

**Prerequisite**: US1 (Configuration Loading) - requires `inbound` configuration with `kind: command`.

**Independent Test**: POST to sidecar `/invoke/{command}` with payload; verify sidecar transforms request, invokes service endpoint, transforms response, and returns to caller with trace spans logged.

**Acceptance Scenarios**:

1. **Given** sidecar configured with inbound command `create-order` mapped to `invokeEndpoint: /orders`, **When** client POSTs to `/invoke/create-order`, **Then** sidecar transforms request, invokes service, and returns transformed response
2. **Given** command invocation with `traceparent` header, **When** sidecar invokes service, **Then** trace context is propagated and response includes trace headers
3. **Given** service returns error response, **When** sidecar receives error, **Then** error is propagated to caller with appropriate HTTP status

---

### User Story 5 - Distributed Tracing (Priority: P2)

As an operator, I want all sidecar operations to emit Zipkin spans so that I can trace message flows across services in the domain.

**Why this priority**: Observability is critical for production but system works without it for development.

**Independent Test**: Configure sidecar with Zipkin URL; perform publish/subscribe operations; verify spans appear in Zipkin with correct parent-child relationships.

**Acceptance Scenarios**:

1. **Given** sidecar configured with `ZIPKIN_URL`, **When** event is published, **Then** sidecar emits span with operation name, trace ID, and tags
2. **Given** sidecar processes event subscription, **When** invoking service, **Then** emits parent-child spans: receive → transform → invoke
3. **Given** `ZIPKIN_URL` is not configured, **When** sidecar operates, **Then** no tracing errors occur (graceful degradation)

---

### User Story 6 - Health & Readiness (Priority: P3)

As an operator, I want the sidecar to expose health and readiness endpoints so that container orchestrators can manage lifecycle.

**Why this priority**: Required for production but manual verification works for PoC.

**Independent Test**: Start sidecar; call `/health` and `/ready` endpoints; verify appropriate responses based on Redis connectivity.

**Acceptance Scenarios**:

1. **Given** sidecar is running with Redis connected, **When** calling `GET /health`, **Then** returns 200 OK with health status
2. **Given** Redis is not connected, **When** calling `GET /ready`, **Then** returns 503 Service Unavailable
3. **Given** sidecar is starting up, **When** calling `/ready` before Redis connected, **Then** returns 503 until connection established

---

### Edge Cases

- What happens when Redis connection is lost during operation? Sidecar logs error and retries with exponential backoff
- How does sidecar handle malformed CloudEvents messages? Logs warning and skips message (at-least-once allows redelivery)
- What happens when configured transformation function doesn't exist? Startup validation fails with clear error
- How does sidecar handle service endpoint timeout or connection refused? Logs error, emits error span, continues processing other messages
- What happens when message payload exceeds size limits? Redis handles via configuration; sidecar passes through

## Requirements _(mandatory)_

### Functional Requirements

#### Configuration (US1)

- **FR-001**: Sidecar MUST load configuration from file path specified by `CONFIG_PATH` environment variable
- **FR-002**: Sidecar MUST validate configuration on startup and fail fast with clear errors
- **FR-003**: Sidecar MUST support `inbound` array with entries containing: `kind` (command|event), `topic`/`command`, `transform`, `invokeEndpoint`
- **FR-004**: Sidecar MUST support `outbound` array with entries containing: `eventType` (for routing lookup), `topic` (target Redis stream), `transform` (optional)

#### Event Publishing (US2)

- **FR-005**: Sidecar MUST expose `POST /publish` endpoint for event publishing (topic resolved from `x-event-type` header via routing config)
- **FR-006**: Sidecar MUST wrap payloads in CloudEvents 1.0 format with required fields (specversion, type, source, id, time, datacontenttype, data)
- **FR-006a**: Sidecar MUST map `x-service-name` header to CloudEvents `source` field
- **FR-006b**: Sidecar MUST map `x-event-type` header to CloudEvents `type` field
- **FR-006c**: Sidecar MUST map `x-correlation-id` header to CloudEvents `correlationid` extension
- **FR-006d**: Sidecar MUST include `x-user-id` and `x-tenant-id` in CloudEvents extensions when headers are present
- **FR-007**: Sidecar MUST include `traceparent` extension in CloudEvents envelope from request header or generate new trace context
- **FR-008**: Sidecar MUST apply configured outbound JSONata transformation before publishing (when transform specified)
- **FR-009**: Sidecar MUST publish to Redis Streams using XADD command
- **FR-009a**: Sidecar MUST resolve target topic from `x-event-type` header using outbound routing configuration
- **FR-009b**: Sidecar MUST return 400 Bad Request if `x-event-type` or `x-service-name` header is missing
- **FR-009c**: Sidecar MUST return 400 Bad Request if no matching route exists for `x-event-type`

#### Event Subscription (US3)

- **FR-010**: Sidecar MUST subscribe to configured inbound topics on startup
- **FR-011**: Sidecar MUST read from Redis Streams using XREAD with blocking
- **FR-012**: Sidecar MUST extract CloudEvents envelope and apply inbound transformation
- **FR-013**: Sidecar MUST invoke configured service endpoint with transformed payload
- **FR-014**: Sidecar MUST propagate `traceparent`, `x-event-type`, `x-correlation-id`, `x-user-id` (if present), `x-tenant-id` (if present) headers to service

#### Command Invocation (US4)

- **FR-015**: Sidecar MUST expose `POST /invoke/{command}` endpoint for command invocation
- **FR-016**: Sidecar MUST route commands to configured service endpoints based on command name
- **FR-017**: Sidecar MUST apply inbound transformation to request and outbound transformation to response
- **FR-018**: Sidecar MUST support request-response pattern with synchronous invocation

#### Distributed Tracing (US5)

- **FR-019**: Sidecar MUST emit Zipkin spans for all operations when `ZIPKIN_URL` is configured
- **FR-020**: Sidecar MUST create parent-child span relationships (receive → transform → invoke)
- **FR-021**: Sidecar MUST include tags for operation type, topic, HTTP URL, and transform function
- **FR-022**: Sidecar MUST gracefully handle Zipkin unavailability without affecting message processing

#### Health (US6)

- **FR-023**: Sidecar MUST expose `GET /health` endpoint returning 200 when running
- **FR-024**: Sidecar MUST expose `GET /ready` endpoint returning 200 only when Redis is connected

### Key Entities

- **CloudEvent**: Message envelope with specversion, type, source, id, time, data, traceparent extension
- **InboundEntry**: Configuration for consuming events or handling commands (kind, topic/command, transform, invokeEndpoint)
- **OutboundEntry**: Configuration for publishing events (topic, transform)
- **SidecarConfig**: Root configuration object with inbound and outbound arrays
- **Span**: Zipkin trace span with traceId, spanId, parentId, name, timestamp, duration, tags

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Events published through sidecar appear in Redis streams within 100ms
- **SC-002**: Subscribed events invoke service endpoints within 200ms of stream message arrival
- **SC-003**: Command invocations complete round-trip (request → transform → invoke → transform → response) within 500ms for typical payloads
- **SC-004**: 100% of operations emit trace spans when Zipkin is configured
- **SC-005**: Sidecar starts and validates configuration within 5 seconds
- **SC-006**: Single trace ID propagates through entire event chain (publish → consume → publish → consume)
- **SC-007**: Invalid configuration fails startup with actionable error messages within 1 second
- **SC-008**: Health endpoints respond within 50ms

## Assumptions

- Redis is available as the message broker (PoC scope)
- JSONata transformations are provided as JavaScript functions in transform.js (PoC) or loaded from mounted files (future)
- Services expose HTTP endpoints for event consumption and command handling
- Zipkin is optional but recommended for observability
- Docker Compose is the deployment mechanism (generated by spas-compose)
- Each service instance pairs with exactly one sidecar instance

## Dependencies

- **006-sidecar-config-generator**: Generates `config.{service}.json` files consumed by sidecar
- **005-spas-compose-cli**: Generates docker-compose.yaml that deploys sidecar alongside services
- **Prototype**: `prototypes/spas-sidecar-prototype/` provides reference implementation

## Out of Scope (PoC)

- gRPC protocol support (Production scope)
- mTLS termination (Production scope)
- Schema validation of messages (Production scope)
- Hot-reload of configuration (atomic swap implemented but not triggered)
- Policy enforcement beyond topic routing (Production scope)
- Idempotency enforcement (Future scope)
